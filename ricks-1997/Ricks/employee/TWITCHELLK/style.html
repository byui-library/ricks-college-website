Elements of Style

A technical report consists of introductory material and definitions of terms and acronyms followed by the body of the report. The body of the report is divided into sections with section headings; the organization of the report aids the reader in understanding the report. A technical report should be readable and understandable. A software program is no different.

The introductory material of a software program consists of a comment block identifying the program and its author. A brief explanation of what the program is supposed to do should also be included.

The definitions of terms and acronyms of a software program typically consist of variable declarations. While variables are declared in more than one location (e.g., more global variables are declared separately from more local variables), the format should be the same, with the exception of subroutine parameters. Each variable should be declared on a separate line with an explanatory comment (if necessary). To maintain readability, subroutine parameters are declared after the subroutine name and explanatory comments are contained in the subroutine comment block. Using descriptive identifiers reduces or eliminates the need for explanatory comments. For example, sum tells us we are adding something; sumOfSquares tells us specifically what we are adding. Use of descriptive identifiers also reduces the need for comments in the body of the source code. For example, sum += x * x; requires explanation. On the other hand, sumOfSquares += userInput * userInput; not only tells us where the item we are squaring came from, but also that we are creating a sum of the squares of those items. If identifiers are chosen carefully, it is possible to write understandable code with very few, if any, comments.

The following convention shall be using for identifiers: Class and structure (struct) identifiers begin with an uppercase letter (ThisIsAClass). Subroutine (function) and variable identifiers begin with a lowercase letter (thisIsASubroutine (), thisIsAVariable). Note that if an identifier consists of more than one word, the words are joined together and each word after the first begins with an uppercase letter. Underscores are not used. All the letters in the constant identifiers are capitalized; underscores are used to separate words (THIS_IS_A_CONSTANT).

A technical paper is divided into sections; the sections of a software program consist of subroutines and classes. Main is a subroutine, although one with special meaning. The section titles consist of additional comment blocks identifying the subroutine or class and explaining the functionality it provides to the program. Subroutine comment blocks also include an explanation of the data passed to the subroutine (inputs) and returned by the subroutine (outputs). Use of white space between subroutines as well as within subroutines enhances readability.

Readability is also enhanced by placing white space around operators. Because of the way printers and video displays handle text, readability is improved by keeping each line of code less than 80 characters long.

Subroutines and classes should be ordered in a program such that they are easy to locate by the reader of the source code. For larger programs, an alphabetical arrangement works well. For shorter programs, following the order in which the subroutines are invoked or objects are instantiated is useful.

To aid the reader in following the structure of the source code, statements should be consistently indented. Because tab stops are not consistent from one editor to another, spaces shall be used instead of tabs. Three spaces work well for an indentation. Each statement within a block of code, defined by curly braces ({}), should be indented the same number of spaces. Each curly brace should be on its own line; this makes them easier to match up. A block of code nested within another block of code should be further indented to distinguish it from other code within the same block.

Comments serve many purposes. Since a comment can be easily read by a programmer and source code, in many cases, must be decoded, one purpose of comments is to clarify complicated code. Comments can be used to convey information to those who will maintain the code. For example, a comment might provide warning that a certain value cannot be changed without impacting other portions of the program. Comments can provide documentation of the logic used in a program. Above all else, comments should add "value" to the code and should not simply restate what is obvious from the source code. The following are meaningless comments and add no value to the source code:

    int i; // declare i to be an integer
    i = 2; // set i to 2
On the other hand, the following comments add value:
    int i; // indexing variable for loops
    i = 2; // skip cases 0 and 1 in the loop since they were processed earlier

"Commenting out" portions of the source code can be an effective debugging technique. However, these sections can be confusing to those who read the source code. The final version of the program should not contain segments of code that have been commented out.

Just as one would expect correct spelling in a technical paper, one should also find correct spelling within a program.

Examples of source code meeting the above style guidelines:

  • Adding two integers supplied by a user
  • Cubing an integer read from a file
  • Adding complex numbers
